Good question — and worth separating from the bug queue, because these are *design* gaps I'd flag even if every error were fixed tomorrow. Roughly in priority order, grounded in what I actually felt while building Mission Control:

**1. Router × data coordination — the biggest hole, and it's self-admitted.** The guide states outright that route/data coordination, route-level lazy chunks, and routing-aware SSR/streaming/hydration are "not implemented by the routing directives." In practice that means every route component is an island that fetches for itself — no loaders that run before navigation, no route-level code splitting, no pending-navigation convention. Every other layer of this framework feels opinionated and complete; routing is currently just URL-state plumbing with fetches bolted inside components. This is where the framework most needs a story, because it's the part every real app leans on hardest. (Related: `route.params['projectId'] ?? ''` is stringly-typed — typed route params would be cheap wins.)

**2. Failure containment.** When a component threw during SSR (my style-object crash), it didn't fail *that render* — it killed the entire Vite dev server process. One bad `style={{...}}` shouldn't require restarting your dev loop. The framework needs render-level error boundaries for SSR, and the dev server needs to isolate render crashes instead of dying with them. `defineServer`'s `onError` catches route handler errors, but render-time exceptions escape fatally.

**3. Tooling that makes the invisible model visible.** This is the strategic one. The framework's thesis is "the compiler understands your code" — which means the *product* isn't the runtime, it's the feedback loop. Right now that loop only exists at build time, as errors, sometimes with wrong locations. The language service exists but is optional and underleveraged. What this framework needs to own: editor squiggles that say "this expression is outside the comprehension envelope" *while you type* (that alone would have prevented three of my eight errors), a why-did-this-update devtools panel over the entity/dirty-propagation graph, and a request-id inspector for `$track`. You can't `console.log` in a component body to debug reactivity — the body runs once — so the framework owes developers a different window into their own program.

**4. Documentation of the envelope itself.** The guide is a good *contract* but has no *cookbook* layer. The rules that bit me — sources don't survive prop boundaries, ternaries can't produce mapped collections, helper args don't carry reactivity — are all unstated limits of the comprehension envelope. There needs to be a reference that enumerates supported derivation shapes (and the blessed workaround for each unsupported one), plus the component-design rules that don't exist in React: which side of a boundary owns a source, when to split vs. inline a derivation.

**5. Testing story — currently zero.** The guide doesn't mention testing at all. A compiler-first framework has a unique problem here: tests must exercise the *compiled* semantics, not the authored source, or they'll lie to you. It needs a first-party harness — render-to-string for components, a controllable data runtime for `$fetch`/`$track`, deterministic scheduler control for assertions about update batching. React has RTL, Solid has its testing library; the absence here means early adopters invent broken patterns.

**6. Escape-hatch depth and interop conventions.** `effect` is deliberately narrow (sync only, strict positions, no deps array) and the volatile-frame fallback for external state is clever but blunt. The framework needs blessed adapters for the libraries people actually combine with UIs — state machines, animation systems, canvas/Three.js — and an exit-animation story for keyed rows (row disposal is immediate; every board drag-drop app wants FLIP transitions). Escape hatches are where frameworks earn trust at the edges.

**7. Production and security conventions.** The deployable artifact of a fullstack `vite build` is undocumented (what serves SSR in production, CDN guidance for streamed HTML), and server functions are exposed at `/_fn/*` with middleware as the *only* auth story — the guide's `x-admin` header check is a toy example. First-class authorization conventions for server functions (public/private split or per-function guards) should exist before anyone ships this publicly.

If I had to bet: #1 and #3 determine whether this stays a research-grade curiosity or becomes genuinely competitive. The core reactivity model and the data layer are already the pleasant parts — the differentiation now has to come from making the compiler's understanding *visible and trustworthy* to the developer, not just correct.
